그룹 스테이지와
사내 컨테스트

회사·단체가 자기들만의 스테이지를 열고, 그 안에서 만든 공연을 서로 리플레이해 순위를 가리는 기능. 무엇을 비공개로 할지, 순위를 무엇으로 셀지, 그리고 지금 코드에서 무엇이 먼저 깨지는지를 정리한다.

대상 keyc-studio · main 상태 결정 완료 · 구현 전 작성 2026-08-11
결론 먼저

① 그룹 스테이지는 “미등재(unlisted)”로 시작한다. “완전 비공개”는 지금 아키텍처에서 지킬 수 없는 약속이다 — 작품 자산의 Storage 읽기가 열려 있기 때문이다(storage.rules:51,60,69). 진짜 기밀은 B2B 유료 단계에서 별도 경로로 만든다.

② 순위는 총 리플레이 수가 아니라 “들어본 사람 수”로 센다. 상품이 걸린 순간 recordPlay의 현재 중복 방지(인스턴스 메모리, 1분)는 방어선이 되지 못한다(functions/index.js:487–504). 화면에는 리플레이 수를 크게 보여주되, 등수는 고유 청취자 수로 정한다.

③ 컨테스트는 기간이 있는 3단계(접수 → 감상 → 발표)로 굴리고, 감상 기간에는 순위를 감춘다. 초반 1등에게 쏠리는 눈덩이를 막고, 기본 정렬을 “아직 안 들은 공연 먼저”로 두어 모두가 고르게 들리게 한다.

“입장은 코드만” + “순위는 고유 청취자”는 P2에서 충돌한다. 참가자가 새 익명 uid를 만들고 자기가 아는 그 코드로 다시 입장하면 멤버가 되고, 그대로 한 표가 더 생긴다. 4절의 방어(1인 1표)는 모집단이 닫혀 있을 때만 성립한다.

v1은 순위가 없으므로 조작 동기가 없어 문제가 되지 않는다. 하지만 순위와 상품을 켜는 순간 이 결정은 재검토 대상이다. 그래서 requiresGoogle 필드를 지금 스키마에 넣어 둔다 — 그때 마이그레이션 없이 켤 수 있도록.

01

지금 구조가 이미 주는 것, 그리고 걸림돌

이 기능은 백지에서 시작하지 않는다. 지금 코드에는 그룹 스테이지에 그대로 쓸 수 있는 구조가 세 가지 있고, 정면으로 부딪히는 전제가 세 가지 있다.

그대로 쓸 수 있는 것

공개 여부가 이미 2축이다. visibility: 'link'(링크로 열 수 있는가)와 discoverable: true(공개 스테이지에 뜨는가)가 분리돼 있다. 이건 우연이 아니라 정확히 우리에게 필요한 축이다 — 그룹 전용 작품은 discoverable: false이기만 하면 listPublicFeed가 자동으로 걸러낸다(functions/index.js:360–363). 공개 스테이지 격리에 새 코드가 거의 필요 없다.

discoverable은 Work 스키마 밖의 필드다. Visibility 타입은 'local' | 'link'뿐이고 (src/work-model/types.ts:204), discoverable은 Firestore 문서에만 있다. 같은 패턴으로 groupIds를 추가하면 스키마 v3도, serialize.ts· portable-work.ts 변경도, 마이그레이션도 필요 없다.

목록은 절대 클라이언트에 열지 않는다는 원칙이 이미 서 있다. allow list: if false와 callable 중계(listPublicFeed)라는 형태가 확립돼 있어, 그룹 스테이지도 같은 모양(listGroupStage)으로 붙이면 된다. 규칙에 그룹 목록 쿼리를 여는 유혹에 빠지지 않아도 된다.

정면으로 부딪히는 것

전제 충돌 1 — “비공개”가 성립하지 않는다

storage.rules는 works/{workId}/art|sound|thumb의 읽기를 if true로 열어 두었다. 의도된 트레이드오프이고 주석에 이유가 잘 적혀 있다 (카카오톡 크롤러, 자산당 Firestore read 비용). 결과적으로 workId를 아는 사람은 그림과 목소리 파일을 직접 받을 수 있다. 여기에 더해 firestore.rules:60–62가 visibility == 'link'인 문서의 get을 누구에게나 허용한다. 즉 지금 구조에서 “그룹 비공개”는 목록이 안 보인다는 뜻이지 내용이 보호된다는 뜻이 아니다.

전제 충돌 2 — 재생 집계가 순위의 근거가 되기엔 약하다

recordPlay의 중복 방지는 const recent = new Map(), 즉 함수 인스턴스의 메모리다(functions/index.js:487). maxInstances: 10이라 인스턴스마다 따로 세고, 콜드 스타트마다 리셋된다. 거기에 익명 로그인이 기본이라 시크릿 창을 열 때마다 새 uid가 생긴다. 공개 스테이지의 “인기순”에는 충분했지만, 상품이 걸린 사내 컨테스트에는 부족하다. 게다가 ENFORCE_APP_CHECK는 기본값이 꺼짐이다 (functions/index.js:57).

전제 충돌 3 — 제품 언어가 아이용이다

공유 게이트는 “보호자 확인”을 요구하고(ShareGateScreen.tsx), 문구 전반이 아이와 보호자를 향해 있다. 회사 컨테스트 참가자는 성인이고, 동료의 목소리가 올라간다. 보호자 동의는 맞지 않고, 대신 임직원 개인정보 처리 동의가 필요해진다. 같은 화면을 그대로 쓰면 법적으로도 어색하고 B2B 구매 담당자에게도 이상하게 보인다.

02

유사 서비스는 이 문제를 어떻게 풀었나

“그룹 안에서만 보이는 작품 모음 + 순위”라는 조합은 새롭지 않다. 교육 도구, 게임 잼, 음원 스트리밍이 각각 다른 각도에서 이미 풀어 놓았고, 서로 다른 부분을 빌려올 수 있다.

서비스 그룹 경계 참여 마찰 평가 방식 키크가 가져올 것
Scratch 스튜디오 스튜디오 단위. 호스트 / 매니저 / 큐레이터 3단 권한. “누구나 추가” 토글로 개방·폐쇄를 바꾼다. 계정 필수, 초대 수락 절차 순위 없음. 좋아요·조회수만 권한 3단계와 “누구나 올릴 수 있는가” 토글. 큐레이터가 남의 작품은 못 내리는 규칙도 그대로 쓸 만하다.
Kahoot 세션 PIN. 게임이 끝나면 소멸 계정 불필요. PIN + 닉네임, 또는 QR 스캔 실시간 순위표 6–8자 코드 + QR로 입장. 사내 공지·슬랙에 그대로 붙일 수 있는 형태가 핵심이다.
Padlet “링크 프라이버시” × “방문자 권한” 2축. 조직 전용 + 조직 대시보드 노출 옵션 링크 또는 참여 코드 반응(별·좋아요) 볼 수 있는 사람과 올릴 수 있는 사람을 분리하는 2축 설계. 하나로 합치면 나중에 반드시 쪼개게 된다.
itch.io 게임 잼 공개. 대신 기간이 경계 계정 필수 기간제 투표 + 평가 큐(무작위로 덜 평가된 작품을 배정) + 표 수를 신뢰도로 쓰는 가중 점수 접수/감상/발표 3단계와 “아직 안 들은 것 먼저” 큐. 늦게 올린 사람이 구조적으로 불리해지는 문제를 이걸로 없앤다.
Spotify (부정 스트리밍 탐지) — — 재생 수와 고유 청취자 수의 괴리를 조작 신호로 본다. 한 곡을 반복 재생하는 소수 계정, 단일 IP 집중을 잡아낸다 순위는 고유 청취자 수, 재생 수는 표시용. 그리고 관리자에게 “한 사람이 몰아준 흔적”을 보여주는 화면.

한 줄로 요약하면: 경계는 Kahoot(코드)에서, 권한은 Scratch(3단계)에서, 축 분리는 Padlet에서, 기간과 탐색 큐는 itch.io에서, 집계 방식은 Spotify에서 가져온다.

03

판단 ① 그룹 스테이지를 어디까지 비공개로 할 것인가

“비공개로 하는 게 좋을 것 같다”는 직감은 맞다. 다만 비공개에는 세 가지 서로 다른 수준이 있고, 셋의 구현 비용이 완전히 다르다. 하나로 뭉뚱그리면 “비공개”라고 써 놓고 실제로는 지켜지지 않는 상태가 된다.

수준 실제로 보장되는 것 뚫리는 지점 구현 비용
A. 공개 지금과 같음. 공개 스테이지에 뜬다 — 0
B. 미등재 v1 권고 그룹 스테이지 목록은 멤버만 본다. 공개 스테이지·검색에 절대 뜨지 않는다 workId(= 공유 링크)를 아는 사람은 작품 자체를 열 수 있다. 썸네일·OG 미리보기도 열린다 낮음 — discoverable:false + 그룹 전용 목록 API
C. 기밀 링크를 알아도 멤버가 아니면 못 연다. 썸네일·OG도 안 나온다 멤버의 화면 녹화·재공유 (기술로 못 막는 영역) 높음 — Storage 경로 신설 + 서명 URL + thumb/shareMeta 차단

왜 v1은 B(미등재)인가

회사 컨테스트에서 실제로 요구되는 것을 뜯어보면 대부분 “우리 회사 콘텐츠가 모르는 사람들 사이에 섞여 나오지 않을 것”이다. 임원 성대모사가 공개 스테이지 인기순 1위에 올라 카카오톡 미리보기로 퍼지는 것 — 그게 실제 공포다. B는 이걸 완전히 막는다. 그리고 B는 기존 아키텍처를 거스르지 않는다.

반대로 C는 storage.rules의 근본 전제를 뒤집어야 한다. 그 주석이 설명하는 비용(자산당 Firestore read, 크롤러 호환)이 그대로 되돌아온다. 첫 버전에서 치를 값이 아니다.

권고

그룹 문서에 privacy: 'unlisted' | 'confidential' 필드를 지금 넣어 두되 v1은 unlisted만 구현한다. 필드가 있으면 나중에 C를 붙일 때 데이터 마이그레이션이 없다.

그리고 UI 문구에서 “비공개”라는 단어를 쓰지 않는다. “공개 스테이지에는 올라가지 않아요. 링크를 받은 사람은 열어볼 수 있어요” 라고 사실대로 쓴다. 이 앱은 이미 ShareGate에서 “완전 익명이라고 쓰지 않는다”는 원칙을 지키고 있다 — 같은 원칙의 연장이다.

C(기밀)를 나중에 만들 때의 설계

미리 방향만 잡아 두면 v1에서 잘못된 길을 덜 든다. 핵심은 함수가 바이트를 중계하지 않고 서명 URL을 발급하는 것이다.

  • 기밀 그룹의 자산은 groupWorks/{groupId}/{workId}/…에 올리고 규칙은 read: if false
  • openGroupWork callable이 멤버십을 확인한 뒤 자산 8개의 서명 URL을 한 번에 반환 (유효기간 1시간)
  • 서명 URL은 GCS 레벨이라 Storage 규칙을 우회한다 — 함수 호출 1회로 작품 하나가 열린다. 바이트 중계(자산당 1회 호출)보다 8배 싸다
  • thumb, shareMeta는 기밀 작품에 대해 404 / 기본 OG로 응답
  • Firestore works/{id}의 get은 visibility == 'link' 대신 멤버십 exists()를 확인
04

판단 ② 순위를 무엇으로 셀 것인가

요청은 명확하다 — “리플레이 수가 많은 걸로 순위를 정한다”. 이 게임 규칙 자체는 좋다. 누르고 듣는 것이 이 제품의 본체이고, 순위가 재생 행위에서 나오는 건 자연스럽다. 문제는 “리플레이 수”의 정의다.

지금 정의로 가면 무슨 일이 일어나나

사내 컨테스트에는 상품이 걸린다. 공개 스테이지의 인기순과 달리 조작 동기가 실재한다. 지금 정의(누적 재생 수, uid당 1분 1회, 인스턴스 메모리 중복 방지)라면 참가자가 취할 수 있는 가장 합리적인 전략은 이렇다.

  • 시크릿 창을 열고 내 작품을 재생한다 → 새 익명 uid → 카운트 1
  • 창을 닫고 다시 연다 → 또 새 uid → 카운트 1
  • 1분 제한은 uid가 바뀌면 무력하다. 인스턴스가 바뀌어도 무력하다
  • 가족·친구에게 링크를 뿌린다 — 미등재라 링크로는 다 열린다

Spotify가 부정 스트리밍을 잡을 때 보는 첫 번째 신호가 정확히 이것이다 — 재생 수는 폭증하는데 고유 청취자 수는 그대로인 패턴. 우리는 탐지할 필요가 없다. 애초에 셀 수 없게 만들면 된다.

두 숫자는 무엇이 다른가

지표 세는 것 30명 회사에서 나올 수 있는 최댓값
리플레이 수 재생 버튼이 눌린 횟수 무한대
고유 청취자 수 서로 다른 사람의 수 30

increment에는 기억이 없다

여기가 핵심이다. 서버는 이미 누가 눌렀는지 알고 있다. recordPlay는 로그인을 요구하고 uid를 손에 쥔 채 시작한다 (functions/index.js:491). 

const uid = request.auth?.uid;
if (!uid) throw new HttpsError('unauthenticated', '로그인이 필요해요');

그런데 바로 다음에 하는 일은 이것이다.

plays: FieldValue.increment(1),   // +1 하고 끝. uid는 버린다

increment는 기억이 없는 연산이다. 숫자에 1을 더할 뿐이라, 100번 눌린 작품이 한 사람이 100번 누른 것인지 100명이 한 번씩 누른 것인지 구분할 방법이 원리적으로 없다. 저장된 게 숫자 하나뿐이기 때문이다.

지금의 1분 제한도 이걸 해결하지 못한다. “얼마나 자주”만 제한하지 “몇 명인지”는 여전히 세지 않기 때문이다. 1분마다 한 번씩 하루를 채우면 1,440이 쌓인다.

그래서 “누가 들었는지”를 적어 둔다

부정을 탐지해 걸러내는 게 아니다. 같은 사람이 두 번 세지지 않는 자료구조를 쓰는 것이다. 숫자 하나 대신 (작품, 사람) 쌍마다 문서를 하나씩 만들고, 문서 ID를 {workId}__{uid}로 고정한다. 같은 사람이 또 들어도 같은 ID라서 문서가 늘어나지 않는다. 

const listenRef = db.doc(`groups/${gid}/listens/${workId}__${uid}`);
const entryRef  = db.doc(`groups/${gid}/entries/${workId}`);

await db.runTransaction(async (tx) => {
  const listen = await tx.get(listenRef);

  // 리플레이 수는 언제나 오른다 — 화면에 크게 보이는 그 숫자
  tx.set(entryRef, { replayCount: FieldValue.increment(1) }, { merge: true });

  if (listen.exists) {
    tx.update(listenRef, { plays: FieldValue.increment(1) });
    return;                    // 이미 센 사람이다. 순위는 안 움직인다
  }

  // 여기 왔다는 건 이 사람이 이 작품을 처음 듣는다는 뜻
  tx.set(listenRef, { workId, uid, firstAt: Date.now(), plays: 1 });
  tx.set(entryRef, { uniqueListeners: FieldValue.increment(1) }, { merge: true });
});

uniqueListeners가 오르는 조건은 딱 하나 — 그 사람의 문서가 아직 없을 때. 판정 로직도, 어뷰징 점수도, 임계값도 없다. 문서가 있느냐 없느냐뿐이다.

숫자로 보면

작품 A의 작가가 시크릿 창을 40번 열어 자기 걸 돌렸고, 작품 B는 동료 25명이 한 번씩 들었다고 하자.

작품 리플레이 수 고유 청취자 수 지금 규칙 새 규칙
A (자가 재생) 48 3 1위 2위
B (25명이 청취) 25 25 2위 1위

두 숫자를 둘 다 저장하고 둘 다 화면에 보여준다. “리플레이 48회”는 그대로 크게 뜬다. 바뀌는 건 등수를 매길 때 어느 쪽을 보느냐뿐이다.

권고 — 지표를 둘로 나눈다

순위 = 고유 청취자 수(uniqueListeners). 그룹 멤버 한 사람이 한 작품에 대해 평생 1을 준다. 두 번째 재생부터는 순위에 영향이 없다.

표시 = 총 리플레이 수(replayCount). 카드에는 지금처럼 “리플레이 1,240회”를 크게 보여준다. 재미와 만족감은 여기서 나온다. 동점일 때의 2차 정렬 기준으로만 순위에 관여한다.

확정 — 둘 중 무엇으로 등수를 매길지는 그룹이 고른다(rankingMetric, 기본 uniqueListeners). 친목 그룹은 총 재생 수가 더 재밌을 수 있다. 두 방식 모두 listens 문서는 똑같이 쌓이므로, 나중에 바꿔도 과거 집계가 살아 있다.

이 조합의 좋은 점은 사용자에게 규칙이 단순하게 들린다는 것이다. “몇 명이 들었나로 1등을 정해요”는 “재생 수로 정해요”만큼 직관적이면서, 조작에 대해 근본적으로 강하다.

고유 청취자로 세기 위한 조건

규칙 왜 구현
Firestore 문서로 중복 제거 메모리 기반은 인스턴스·콜드스타트에 무력하다. 순위의 근거는 영속적이어야 한다 groups/{gid}/listens/{workId}__{uid} 문서를 트랜잭션으로 생성. 처음 생성될 때만 uniqueListeners를 +1
멤버만 집계 링크를 외부에 뿌려도 순위가 안 움직인다. 미등재의 유일한 구멍이 순위에 닿지 않게 한다 recordPlay에 groupId를 받고 멤버십 exists() 확인
본인 작품 제외 자기 표는 의미가 없고, 자가 재생 유인을 없앤다 entry.authorUid === uid면 replayCount만 올리고 청취자에서 뺀다
완주 조건 0.5초 눌렀다 나가는 것을 “들었다”로 세면 전수 청취가 무의미해진다. Spotify의 30초 규칙과 같은 발상 재생 완료 이벤트일 때만, 또는 durationMs의 80% 이상 재생했을 때만 집계
Google 로그인 요구(옵션) 익명 uid는 기기·브라우저 단위다. 같은 사람이 폰과 PC에서 2표를 낼 수 있다 그룹 설정 requiresGoogle. B2B 그룹은 기본 켜짐, 친목 그룹은 꺼짐
App Check 강제 스크립트로 callable을 직접 두드리는 경로를 막는다. 지금은 꺼져 있다 ENFORCE_APP_CHECK=true — 컨테스트 기능 공개 전 필수

그룹이라서 특별히 강한 이유 — 닫힌 모집단

“새 익명 uid를 만들면 새 사람으로 세지는 것 아닌가”가 남는 질문이다. 여기서 그룹의 성질이 결정적으로 작용한다.

공개 스테이지는 모집단이 열려 있어서 청취자가 몇 명이든 이상하지 않다. 하지만 그룹은 멤버 명단이 있는 닫힌 집단이다. 집계를 멤버로 한정하면:

  • 새 익명 uid를 만들어도 그 uid는 그룹 멤버가 아니라서 애초에 집계 대상이 아니다
  • 새 uid로 그룹에 들어오려면 입장 코드가 필요하고, requiresGoogle이나 도메인 제한을 켜두면 회사 계정이 또 있어야 한다
  • 30명 그룹에서 고유 청취자 31이 나오는 것 자체가 불가능해진다 — 상한이 명단으로 정해진다
두 조건은 세트다

“1인 1표로 센다”와 “모집단이 닫혀 있다”가 같이 있어야 방어가 완성된다. 1인 1표만으로는 계정을 늘리면 뚫리고, 멤버 한정만으로는 한 멤버가 1,000번 눌러 이긴다. 둘 중 하나만 구현하면 나머지 절반이 그대로 구멍으로 남는다.

덤으로 얻는 것

이 listens 문서는 순위 방어를 위한 것이지만, 동시에 “내가 아직 안 들은 공연”을 정확히 알려준다. 판단 ④의 탐색 큐가 공짜로 따라온다. 하나의 문서가 두 가지 문제를 푼다.

보상 설계로 조작 동기를 줄이기

기술적 방어보다 싸고 효과적인 수단이 하나 더 있다. 상을 1등 하나로 몰지 않는 것이다. itch.io의 평가 큐가 노리는 것도 결국 참여 자체에 보상을 주는 구조다.

  • 인기상 — 고유 청취자 1위 (본 게임)
  • 청취왕 — 남의 공연을 가장 많이 들은 사람. listens를 uid로 세면 그냥 나온다
  • 완주 배지 — 그룹의 모든 공연을 다 들은 사람 전원
  • 첫 무대상 — 처음 참가한 사람 중 최고 순위

상이 여러 개면 “1등을 위해 카운트를 조작한다”의 기대 이익이 떨어지고, 전원이 전부 듣게 만드는 힘이 생긴다. 회사 이벤트의 실제 목적이 “1등 뽑기”가 아니라 “서로 보게 하기”라는 걸 생각하면 이쪽이 본질에 더 가깝다.

주의 — 관람자를 왜 카운트에서 빼는가

“구경만 하는 사람”의 재생을 순위에 넣으면 링크 유출이 곧 표 조작이 된다. 관람자는 듣되 순위에는 영향을 주지 않는다. 화면에서도 그렇게 알려준다 — “참가자만 순위에 반영돼요”. 이건 감출 일이 아니라 공정함의 근거로 보여줄 일이다.

06

판단 ④ 컨테스트를 어떻게 굴릴 것인가

“그냥 계속 열려 있고 재생 수가 계속 쌓인다”는 컨테스트가 아니다. 먼저 올린 사람이 무조건 이긴다. 노출 시간이 곧 점수이기 때문이다. itch.io의 잼 구조가 이 문제를 기간으로 푼다.

단계 1 · 반나절 준비 주최자가 그룹을 만들고 코드·QR을 받는다. 참가자 입장 시작. 스테이지는 아직 비어 있다.
단계 2 · 3–5일 접수 제출과 감상이 동시에 열린다. 순위는 감춘다. “n명이 들었어요”만 보인다.
단계 3 · 2일 감상 제출 마감. 기본 정렬은 아직 안 들은 공연 먼저. 늦게 올라온 작품이 여기서 따라잡는다.
단계 4 · 고정 발표 순위를 고정 저장하고 공개. 이후 재생은 순위를 바꾸지 않는다. 결과 카드를 공유한다.

감상 기간에 순위를 감추는 이유

실시간 순위표를 띄우면 눈덩이 효과가 생긴다. 1위에 오른 작품이 상단에 노출되고, 노출됐으니 더 들리고, 더 들려서 더 위로 간다. 사내 이벤트에서는 이게 “목소리 큰 팀이 이기는 게임”으로 체감된다. 발표 단계에서 한 번에 공개하는 편이 극적이기도 하고 공정하기도 하다.

대신 감상 기간에는 다른 숫자를 보여준다 — “내가 12개 중 7개 들었어요”. 개인 진행률은 눈덩이를 만들지 않으면서 끝까지 듣게 만드는 동기가 된다.

기본값은 감춤, 하지만 토글로 남긴다

친목 그룹은 실시간 순위가 더 재밌다. 그룹 설정에 revealRanking: 'live' | 'onClose'를 두고 기본은 onClose. 컨테스트를 만들 때 주최자가 한 번 고르게 한다.

“아직 안 들은 것 먼저” 정렬

itch.io의 평가 큐를 키크 방식으로 옮긴 것이다. 그룹 스테이지의 기본 정렬을 최신순도 인기순도 아닌 미청취 우선으로 둔다. 

// 그룹 스테이지 정렬 순서
1. 내가 아직 안 들은 것        ← listens 문서가 없는 것
2. 그중 고유 청취자가 적은 것   ← 노출 형평성
3. 그다음 제출이 빠른 것

// 다 들었으면 자동으로 "많이 들은 순"으로 전환

이 정렬은 순위 조작 없이도 모든 작품이 비슷한 노출을 받게 만든다. 판단 ②의 listens 문서를 그대로 쓰므로 추가 저장 비용이 없다.

D-1 그룹 생성, 도메인 제한 설정, 슬랙에 코드+QR 공지 코드 입력 → 입장 완료. “7월 5일까지 공연을 올려주세요”
D+0 ~ D+4 중간에 “아직 3명 남았어요” 리마인드 만들고 제출. 남의 공연을 듣기 시작. 순위는 안 보임
D+5 접수 마감 (자동) “12개 중 7개 들었어요” 진행률. 미청취 우선 정렬
D+7 발표 (자동). 결과 화면을 회의실 스크린에 띄운다 1·2·3위 공개 + 청취왕 + 완주 배지. 결과 카드 공유
07

데이터 모델

핵심 결정은 하나다 — 제출작을 works에 필드로 붙여 정렬하지 않고, 그룹 하위 컬렉션 entries에 카드 정보를 비정규화해 둔다. 

// ★ = v1에서 값은 쓰되 UI는 만들지 않는다 (P2에서 켠다)

groups/{groupId}
  name, ownerUid, createdAt
  privacy       : 'unlisted'                    // 'confidential'은 P3
  join          : { codeHash, codeHint, rotatedAt,
                    requiresGoogle: false,      // ★ 코드만으로 입장
                    emailDomain: null }         // ★ P2+
  limits        : { members: 100, entries: 200 }
  submitPolicy  : 'members' | 'admins'          // Scratch의 "누구나 추가" 토글
  contest       : { phase, submitClosesAt, stageClosesAt,
                    rankingMetric: 'uniqueListeners' | 'replayCount',
                    revealRanking: 'onClose' }  // ★ 전부 P2
  counts        : { members, entries }
  finalRanking  : [{ workId, rank, uniqueListeners }]  // ★ 발표 시 고정

groups/{groupId}/members/{uid}
  role, nick, joinedAt, lastSeenAt
  listenedCount                                 // 청취왕 상용

groups/{groupId}/entries/{workId}
  workId, authorUid, authorNick, title, hint, durationMs
  submittedAt, status: 'active' | 'removed'
  uniqueListeners, replayCount, lastPlayedAt    // 정렬 키가 여기 있다

groups/{groupId}/listens/{workId}__{uid}
  workId, uid, firstAt, plays                   // 존재 = 1표

joinCodes/{CODE}
  groupId, disabled, expiresAt                  // 클라이언트 read 차단

works/{workId}
  + groupIds : [groupId]                        // 최대 3개. 규칙과 정리용
  + discoverable : false                        // groupIds와 독립적인 축
  + expiresAt : null                            // 그룹 제출이면 강제로 null

왜 works에 필드를 붙이지 않는가

항목 works에 groupId 추가 entries 하위 컬렉션 권고
복합 인덱스 현재 4개 → groupId × 정렬 2 × 작성자 필터로 8개 이상. 그룹 정렬 축이 늘 때마다 배로 는다 groupId가 경로에 있어 인덱스에서 빠진다. 정렬 축 조합만큼만
한 작품 여러 그룹 array-contains + orderBy 조합 제약에 걸린다 그룹마다 entries 문서가 따로. 그룹별 순위가 독립적이다
그룹 순위와 공개 순위 replayCount 하나를 공유. 그룹 안에서만의 순위를 못 만든다 그룹별 uniqueListeners가 따로 쌓인다
스테이지 한 페이지 읽기 works 스캔 + workStats getAll entries 12건 read로 끝. 카드 정보가 문서 안에 있다
작품 삭제 시 문서가 사라지면 그룹 순위 이력도 사라진다 status: 'removed'로 남는다. 발표 뒤 삭제해도 순위 기록이 유지된다

필요한 인덱스

entries는 특정 그룹 아래 있는 컬렉션이므로 COLLECTION 범위 인덱스 하나가 모든 그룹에 적용된다. works의 인덱스 4개는 건드리지 않는다. 

entries : status ASC, uniqueListeners DESC, replayCount DESC, __name__ DESC
entries : status ASC, submittedAt DESC, __name__ DESC
listens : uid ASC, firstAt DESC          // 청취왕 집계

비용 감각

30명 × 20작품 그룹 하나가 한 번의 컨테스트에서 만드는 양: listens 문서 최대 600개, 트랜잭션 600회(1인이 전부 들었을 때), 스테이지 조회는 페이지당 12 read. Firestore 무료 할당량(일 5만 read / 2만 write) 안에서 회사 수십 개를 동시에 굴릴 수 있다. 이 설계의 비용은 문제가 아니다.

서버와 보안 규칙

새 Cloud Functions

함수 하는 일 검사

보안 규칙 방향

기존 원칙을 그대로 이어간다 — list는 열지 않고 callable이 중계한다. 규칙은 “쓰기 차단”과 “최소한의 get”만 담당한다. 

match /groups/{gid} {
  allow get   : if isMember(gid);       // 이름·기간 표시용
  allow list  : if false;
  allow write : if false;               // 전부 Functions를 통한다

  match /members/{uid} {
    allow get   : if request.auth.uid == uid || isAdmin(gid);
    allow list  : if false;             // 멤버 명단도 callable로
    allow write : if false;
  }
  match /entries/{workId} { allow get: if isMember(gid);
                            allow list, write: if false; }
  match /listens/{id}     { allow read, write: if false; }
}

match /joinCodes/{code}   { allow read, write: if false; }

// 그룹 전용 작품은 클라이언트 get에서도 걸러야 한다 (기밀 단계)
match /works/{workId} {
  allow get: if resource.data.visibility == 'link'
             && (!resource.data.get('groupOnly', false) || isMemberOfAny(...));
}
규칙에서 exists()를 남발하지 않는다

isMember()는 exists() 호출이고 규칙 평가마다 Firestore read가 청구된다. 그래서 목록 조회는 규칙이 아니라 callable에서 멤버십을 한 번만 확인하도록 설계했다. 규칙의 get은 단건 조회 경로에만 남긴다.

09

화면

하단 탭은 지금 3개(홈·스테이지·만들기)다. 탭을 늘리지 않는다. 그룹은 스테이지 안의 전환으로 넣는다 — 스테이지가 여러 개가 됐을 뿐이라는 모델이 사용자에게 가장 자연스럽다. 

/feed                 스테이지 — 상단에 [모두] [우리 회사 🔒] 전환
/g/:groupId           그룹 스테이지 (미청취 우선 정렬, 진행률)
/g/:groupId/rank      순위 — 발표 단계에서만 열린다
/g/:groupId/manage    운영 — 코드·QR, 기간, 멤버, 내리기
/g/join?code=XXXX     코드 입장 (딥링크 · QR 대상)

그룹 스테이지에서 기존 FeedScreen과 달라지는 부분

  • 헤더가 그룹 이름 + 남은 기간 + 내 진행률(“12개 중 7개 들었어요”)
  • 정렬 세그먼트가 [아직 안 들은 것] [최신] [많이 들은 순] — 마지막 항목은 발표 후에만
  • 카드에 들은 표시(체크). 안 들은 카드가 시각적으로 더 눈에 띄어야 한다
  • feed-badge가 “공개” 대신 “우리 회사만”
  • 발표 전에는 순위 숫자를 감추고 “n명이 들었어요”만

FeedScreen의 커서 페이지네이션·디바운스 검색·중복 방지 로직은 그대로 재사용할 수 있다. 데이터 출처만 listGroupStage로 바꾼다.

제출 흐름

기존 ShareGate를 재사용하되 목적지 선택을 앞에 둔다. 여기가 discoverable이 갈리는 지점이다. 

어디에 올릴까요?  (여러 개 고를 수 있어요)
  ☑ 마케팅팀 여름 콘테스트     → groupIds 에 추가
  ☐ 전사 창립기념 스테이지      → groupIds 에 추가  (최대 3개)
  ☐ 모두의 스테이지            → discoverable: true

기본값은 지금 보고 있는 그룹 하나만 체크된 상태.
"모두의 스테이지"는 언제나 꺼진 채로 시작한다 —
회사 콘텐츠가 실수로 공개되는 방향의 기본값을 두지 않는다.

그룹이 하나라도 체크되면 공유 기간 선택은 숨기고 expiresAt: null 로 고정한다.

groupIds와 discoverable은 독립적인 축이다. 그룹에 올리면서 공개 스테이지에도 올릴 수 있고, 그룹별 entries 문서가 따로 생기므로 같은 작품이 그룹마다 다른 순위를 가진다.

결과 화면

WorkCardScreen이 이미 공유용 카드 이미지를 만든다. 같은 렌더러로 “우리 회사 콘테스트 1위” 결과 카드를 만들면 사내 슬랙에 퍼지는 자연 확산 경로가 생긴다. B2B에서 이게 가장 싼 마케팅이다.

11

로드맵

P1 그룹 스테이지 (2–3주) — v1 확정 범위

순위 없이 먼저 내보내는 것이 이 단계의 핵심이다. 그룹 경계와 집계 정확도가 검증되기 전에 상품이 걸리면 안 되고, 순위가 없으면 “입장은 코드만”의 위험도 실현되지 않는다.

서버

  • createGroup — Google 계정 필수, 계정당 3개 제한, 8자 코드 발급
  • joinGroup — 코드 조회, 멤버 100명 상한 검사, 시도 횟수 제한
  • listGroupStage — 멤버십 확인 후 entries 한 페이지 + 내 청취 여부
  • submitToGroup / withdrawEntry — 작품 200개 상한, expiresAt: null 강제
  • recordPlay 확장 — groupId 수신, 문서 기반 중복 제거, 본인 작품 제외, 완주 조건

클라이언트

  • /feed 상단 [모두] / [그룹] 전환, /g/:groupId, /g/join?code=
  • ShareGate에 제출 대상 다중 선택 + 그룹일 때 만료일 숨김 + 문구 분기
  • 카드에 청취 표시, 헤더에 “n개 중 m개 들었어요” 진행률

10절의 P1 결함 6건

avatar의 discoverable 의존, recordPlay 메모리 중복 제거, ENFORCE_APP_CHECK, publishWork의 discoverable: true 하드코딩, 만료일 충돌, unshareWork의 고아 entries — 전부 이 단계에서 처리한다. 하나라도 남기면 그룹 스테이지가 조용히 잘못 동작한다.

P2 컨테스트 (2주)

기간 3단계, 순위 고정 저장, 상(인기상·청취왕·완주 배지), 결과 카드, 운영 화면(코드 회전·기간 변경·내리기). 미청취 우선 정렬도 여기서.

P2+ B2B 도입 마찰 제거 (1–2주)

이메일 도메인 제한, 관리자 승인, 참가자 CSV 내보내기, 성인용 동의 문구 분기. 회사에 파는 데 필요한 건 기능이 아니라 이 마찰 제거다.

P3 기밀 모드 (유료 · 3주+)

groupWorks/** 경로, 서명 URL, OG·썸네일 차단, 감사 로그, 보존 기간 후 일괄 삭제. 수요가 확인된 뒤에 만든다.

12

아직 안 정한 것

기능 설계에 필요한 결정 12개는 확정 사항에 정리했다. 아래 둘은 구현을 막지 않지만 P2 전에는 답이 있어야 하는 것들이다.

  1. 과금 모델은?

    무료 티어에서 어디까지 열 것인지가 P3의 우선순위를 정한다. 추천: 30명 이하·컨테스트 1개 무료, 그 이상과 기밀 모드·도메인 제한이 유료. 도메인 제한은 회사가 가장 확실하게 돈을 내는 기능이다.

  2. 임직원 목소리에 대한 동의는 누가 받나?

    회사가 직원에게 받는 것이 맞지만, 앱도 수집 주체다. 추천: 그룹 생성 시 주최자가 “참가자 동의를 확보했음”을 확인하고, 참가자에게도 제출 시점에 별도 고지. 일반 공개 전 법률 검토 필요 — ShareGateScreen 주석에 이미 같은 취지가 적혀 있다.
