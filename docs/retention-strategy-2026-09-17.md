# 키크 재방문 개선과 그룹·개인 집중 전략

작성일: 2026-09-17. 분석 대상: 현재 저장소의 프런트엔드, Firebase Functions, 접근 규칙, 기존 설계 문서.

## 1. 제안하는 방향

**다음 검증 주기에는 그룹 중심으로 집중하되, 목표를 ‘그룹 기능 확대’가 아니라 ‘같은 주최자가 다음 회차를 다시 여는 경험’으로 잡는 것을 권한다.** 개인 창작기는 그룹 참여에도 필요한 공통 기반이므로 첫 완성과 재창작을 쉽게 만드는 데 투자한다.

제품의 현재 강점은 키캡·소리·그림·리플레이를 조합한 짧은 창작 경험이다. 그러나 구현과 성공 기준이 첫 작품의 완성·공유에 집중돼 있다. 공유 다음에 무엇을 기다리고, 누구의 반응을 확인하고, 무엇을 다시 만들지에 대한 연결이 약하다. 새로운 재질이나 효과보다 이 연결을 먼저 검증해야 한다.

그룹에는 이미 서로 아는 사람과 초대할 주최자가 있다는 이점이 있다. 개인 공개 피드보다 초기 관객을 확보하기 쉬울 것이라는 **전략 가설**이다. 아직 그룹의 재방문 우위나 사업성을 입증한 데이터는 없다. 회사 워크숍처럼 사용 자체가 드문 용도라면 그룹을 강화해도 일간 재방문은 높아지지 않을 수 있다.

추천하는 첫 사용 장면은 **100명 이하 조직 안의 5~20명 팀이 주간·격주 모임에서 진행하는 짧은 창작 놀이**다. 회사 전체 행사, 단순 경품 추첨, 어린이 공개 창작 커뮤니티를 한꺼번에 공략하지 않는다. ‘매번 만들어서 동료에게 보여줄 이유가 있는가’를 확인할 수 있는 좁은 장면부터 시작한다.

다음 작업의 우선순위는 다음과 같다.

1. 재방문의 대상과 주기를 구분하고, 첫 완성까지의 이탈을 측정한다.
2. 그룹의 비공개 약속과 실제 접근 범위, 청취와 투표의 의미를 맞춘다.
3. 그룹 진입 → 만들기 → 제출 → 감상 → 결과 → 다음 회차를 연결한다.
4. 같은 사용자가 두 번째 작품을 만들고 같은 주최자가 두 번째 행사를 여는지 확인한다.
5. 이 결과를 보고 그룹 투자 확대 또는 개인 중심 전환을 결정한다.

## 2. 분석 범위와 판단의 한계

사용자가 알려준 ‘재방문이 매우 낮다’는 상황을 출발점으로 삼았다. 실제 방문자 수, D1/D7, 유입 경로별 코호트, 그룹 개최 이력, 운영 로그에는 접근하지 않았다. 따라서 아래에서 **코드 사실**, **원인 가설**, **제안**을 구분한다. 낮은 재방문의 원인을 코드만으로 확정하지 않는다.

이번 분석은 정적 코드 검토와 기존 자동 검증에 기반한다. 배포된 규칙이 저장소와 같은지, 모바일 실기기의 녹음·재생, 실제 사용자 행동은 확인하지 않았다. 기존 테스트는 24개 파일·203개 항목 모두 통과했고 `npm run typecheck`도 통과했다. 이 결과가 그룹 접근 제어, 실제 투표의 공정성, 재방문 효과를 보증하지는 않는다.

기존 [그룹 설계 문서](group-stage-design.html)도 미등재와 기밀 공개를 구분하고, 전수 감상과 평가의 차이를 논의한다. 이번 문서는 과거 설계를 새 결함으로 취급하기보다, **현재 사용 목적이 회사의 비공개 투표·뽑기로 확장되면서 재검토해야 할 전제**를 정리한다. 기존 [로드맵](roadmap_temp.md)의 구상과 실제 구현도 구별했다.

## 3. 현재 구현에서 읽히는 사용자 흐름

| 사용자 | 현재 경로 | 재방문 관점에서 끊기는 지점 |
| --- | --- | --- |
| 첫 개인 창작자 | 홈 → 최초 사용 안내 → 키캡 편집 → 무대 → 공연 → 작품 카드 → 공유 설정 | 완성 후 다음 과제·반응 확인·두 번째 작품으로 가는 연결이 약함 |
| 링크 감상자 | 작품 열기 → 리플레이 → 직접 눌러보기·비밀 찾기 → 친구에게 전달 / 나도 만들기 | ‘나도 만들기’는 홈으로 이동하며 원작을 이어받지 않음 |
| 그룹 참가자 | 코드 입장 → 그룹 작품 목록 → 작품 감상 → 그룹으로 돌아가기 | 그룹 화면에서 제출할 작품 만들기로 바로 이어지는 행동이 없음 |
| 그룹 주최자 | 이름 입력 → 그룹 생성 → 코드 전달 → 참가자·작품·청취 집계 확인 | 회차 마감, 결과 확정, 다음 회차 개최의 운영 흐름이 없음 |

그룹 제출은 작품 카드의 공유 설정에서 내 그룹을 다시 선택하는 방식이다. 그룹에서 시작한 목적이 편집기와 제출 화면까지 이어지는 구조는 현재 확인되지 않는다. 개인 창작 경로에 그룹 제출이 마지막 선택지로 붙어 있는 형태다.

### 이미 갖춘 자산

- 새 작품에는 기본 색·소리·움직임이 들어 있다. 완전히 빈 캔버스에서 시작하는 문제는 이미 완화돼 있다.
- 결정론적 리플레이, 직접 눌러보기, 비밀 반응은 단순 정적 작품 공유와 구별되는 경험이다.
- 로컬 저장과 자동 저장, 선택적 계정 백업·복구 코드가 존재한다. ‘저장 기능이 없다’는 진단은 맞지 않는다.
- 익명 계정으로 그룹을 만들고 참가할 수 있으며, 그룹별 청취 기록은 중복 집계를 제한한다.
- 공개 피드와 그룹 목록을 구분하고, 첫 그룹 선택 시 공개 피드 노출을 끄는 배려가 들어 있다.

이 기반을 유지하면서 다음 행동을 연결하는 것이 우선이다.

## 4. 재방문을 약하게 만드는 핵심 가설

### 4.1 첫 방문의 성공과 재방문의 성공이 다르다

**코드 사실:** README의 성공 기준은 ‘작품 1개 완성 후 공유’다. 홈은 오늘의 미션, 새로 만들기, 내 작품으로 구성된다. 미션은 날짜에 따라 선택되는 문구이며, 미션 참가·완료·이력과 작품을 연결하는 모델은 확인되지 않는다.

**가설:** 사용자는 첫 작품을 공유하면 할 일을 마쳤다고 느낀다. 다시 왔을 때도 새로 만들기 외에는 눈에 띄는 이유가 적다. 오늘의 미션이 바뀌어도, 다음 방문 전에 그 변화를 알거나 기다릴 장치는 약하다.

**제안:** 개인의 핵심 성공을 ‘다른 날 두 번째 작품 완성’, 그룹의 핵심 성공을 ‘같은 주최자의 다음 회차 실제 개최’로 추가한다. 홈에는 사용자 상황에 맞춰 진행 중인 회차, 내 작품에 생긴 변화, 이어 만들기 중 가장 관련 있는 행동을 먼저 보여준다.

### 4.2 만드는 비용에 비해 받는 반응이 약할 수 있다

**코드 사실:** 만들기·무대·공연·카드·공유가 여러 화면으로 나뉜다. 최초 만들기에서는 안내 화면을 먼저 거친다. 공유 완료 화면은 링크 복사·감상·홈 이동을 제공한다. 기본 키캡은 있지만, 목적별 완성 예시를 골라 한 부분만 바꾸는 빠른 흐름은 현재 확인되지 않는다.

**가설:** ‘15초 작품’은 재생 길이를 말할 뿐 제작이 15초에 끝난다는 뜻은 아니다. 업무 중 잠깐 참여하려는 사람에게 제작 부담이 클 수 있다. 반대로 편집을 좋아하는 개인에게는 이 과정이 가치일 수 있으므로 실제 이탈 단계로 판단해야 한다.

**제안:** 그룹용 첫 경험은 예시 선택 → 소리 또는 색 하나 변경 → 미리보기 → 해당 회차 제출로 단축한다. 처음에는 마이크 없이도 완성할 수 있게 한다. 상세 편집은 유지하되 빠른 경로에서 필수가 되지 않게 한다. ‘첫 완성까지 2분 이내’는 검증할 목표이며 현재 성능 측정값이 아니다.

### 4.3 감상은 같은 세션 안에서 끝나기 쉽다

**코드 사실:** 감상 후 ‘나도 만들기’는 `/`로 이동한다. 원작 복제나 `remixOf` 계보는 현재 구현에서 확인되지 않는다. 비밀 발견 수는 화면 상태이며 직접 눌러보기를 다시 시작하면 초기화된다.

**가설:** 감상자가 창작자로 넘어가는 순간에 목적과 재료를 잃는다. 비밀 찾기는 체류 시간을 늘릴 수 있지만, 다음 날 돌아올 이유까지 자동으로 만들지는 않는다.

**제안:** 우선 자기 작품 복제와 운영자가 제공한 재사용 가능한 예시 변형을 제공한다. 이후 원작자의 재사용 설정을 갖춘 리믹스를 검증한다. 비밀 찾기는 개인용 작은 수집·도전 이력과 연결할 수 있지만, 재방문 효과가 확인되기 전 대규모 보상 시스템은 만들지 않는다.

### 4.4 그룹은 목록이 있지만 반복 행사 단위가 없다

**최초 분석 당시 코드 사실:** 그룹 생성은 `contest.phase`, `submitClosesAt`, `stageClosesAt`, `revealRanking`을 저장했지만 회차 전환·마감·결과 확정 경로는 없었다. 아래 P1 구현에서 phase 검사, 결과 스냅샷, 다음 회차 전환을 추가했다. 정식 투표·추첨은 여전히 구현 대상이 아니다.

**가설:** 주최자가 다음 참여 주제, 마감, 발표, 재개최를 앱 밖에서 모두 관리해야 한다. 첫 행사에 성공해도 다음 행사를 여는 부담이 줄지 않는다. 같은 방에 작품만 계속 쌓이면 새로 할 일이 명확해지지 않는다.

**제안:** 그룹은 오래 유지되는 사람들의 공간, 회차는 시작과 끝이 있는 활동으로 분리한다. 결과 화면에 다음 회차 복제와 다음 주제를 연결한다. 데이터 필드가 존재하는 것과 실제 운영 기능이 존재하는 것은 다르므로, 현재 `contest` 필드를 완료된 기능으로 계산하지 않는다.

### 4.5 사용자의 정의가 섞여 있다

**코드 사실:** README와 기존 로드맵은 어린이 창작을 중심에 둔다. 그룹은 회사·워크숍·회식에도 쓰려는 방향이 추가돼 있으며, 공개 공유에는 보호자 확인 맥락이 남아 있다.

**가설:** 어린이의 창작 놀이, 성인의 키캡·소리 취미, 회사 행사의 참여 도구는 동기와 사용 빈도가 다르다. 한 홈과 같은 완료 흐름으로 모두를 설득하기 어렵다.

**제안:** 당장 앱을 둘로 나누지 말고, 그룹 초대 진입에는 해당 행사의 목적·참여 버튼을, 개인 진입에는 즉시 체험·만들기를 보여준다. 메시지와 시작 경로를 분리하고 창작 엔진은 공유한다. 개인 실험도 ‘모든 개인’이 아니라 실제 재사용자에게서 발견한 한 사용 장면으로 좁힌다.

## 5. 그룹을 키우기 전에 맞춰야 할 두 가지 약속

### 5.1 현재 ‘그룹만’은 작품 자체의 기밀 접근 제어가 아니다

**확인된 구현:** 그룹 목록 API는 멤버십을 검사한다. 반면 작품 문서는 `visibility == 'link'`이면 인증 없이 읽을 수 있다. 그룹 제출도 이 visibility를 사용한다. 공유용 그림·소리·썸네일의 Storage 읽기는 열려 있다. `discoverable: false`는 공개 피드에서 빠지는 조건이며 작품 접근 권한은 아니다.

따라서 현재 상태는 **그룹 목록은 참가자 전용이고, 개별 작품은 링크를 아는 외부인도 접근 가능한 미등재 공유**다. 이것은 기존 설계 문서에 명시된 선택이다. 다만 회사 이용자가 ‘조직 밖에서는 볼 수 없다’고 이해한다면 그 기대와 다르다.

회사 중심으로 확대할 때 권하는 방향은 다음과 같다.

1. 현재 문구에서 목록 비노출과 작품 접근 제한을 구별한다. 안내 문구만 고친 것으로 기밀 공유가 구현됐다고 보지 않는다.
2. 비공개 그룹 작품에는 서버에서 작성자 또는 허용 그룹의 현재 멤버인지 검사하는 읽기 경로를 둔다. 공개 작품과 비공개 작품의 공개 정책을 명시적으로 분리한다.
3. 문서뿐 아니라 오디오·그림·썸네일, OG 응답, 캐시, 파일 다운로드 경로도 같은 정책을 적용한다. 공개 다운로드 주소를 반환하는 구조가 남으면 문서 규칙만 바꾸어서는 충분하지 않다.
4. 기존 공개 경로의 자산·URL도 이관 또는 무효화 범위에 포함한다. 이미 외부에 저장된 사본까지 회수할 수 있는 것처럼 설명하지 않는다.
5. 비멤버의 직접 작품 URL 접근, 탈퇴·강퇴 후 접근, 다른 그룹 멤버, 공개/비공개 중복 제출을 회귀 검증한다.

권한을 확인하는 읽기 경로가 필요하다는 기술적 근거는 [Firebase Storage 보안 규칙 문서](https://firebase.google.com/docs/reference/security/storage)를 참고했다. 위의 구체적인 문제 판정은 외부 문서가 아니라 이 저장소의 규칙과 업로드 코드를 근거로 한다.

### 5.2 완주자 수, 선호 투표, 무작위 뽑기를 분리한다

현재 `recordGroupPlay`는 자기 작품을 제외하고, 그룹 멤버가 작품을 끝까지 재생했다고 보고하면 작품·uid별 한 번 `uniqueListeners`를 증가시킨다. 명시적으로 ‘이 작품을 선택한다’는 투표가 아니다.

참가자 N명이 각자 한 작품을 올리고 모두가 남의 작품을 완주하면, 각 작품의 고유 청취자 수는 N−1로 같아진다. 현재 방식은 서로 듣기를 유도하는 데 의미가 있지만 선호 우열을 가르는 방식으로는 맞지 않는다. 반복 재생 횟수를 기준으로 바꾸면 노출·시간·외부 링크 배포의 영향이 더 커진다.

| 목적 | 적절한 규칙 | 현재 집계의 역할 |
| --- | --- | --- |
| 서로 감상하는 놀이 | 몇 작품을 들었는지 진행 상황 표시 | 고유 청취자 수를 감상 지표로 유지 |
| 선호 작품 투표 | 회차별 유권자·선택 수·자기 작품 허용 여부·마감·동률 규칙을 정하고 별도 표 저장 | 청취는 참여 조건 또는 참고 자료로만 사용 |
| 참가자 뽑기 | 자격을 갖춘 참가자 집합에서 서버가 무작위 추첨하고 결과 확정 | 필요하다면 최소 감상 수를 자격 조건으로 사용 |

추첨은 많이 반복 재생한 사람에게 확률을 더 주는 방식으로 시작하지 않는다. 참가자 자격을 고정하고, 누구를 몇 명 뽑는지 먼저 합의하며, 중복 실행으로 결과가 바뀌지 않게 한다. 주최자가 보기 좋은 결과가 나올 때까지 재추첨할 수 있는 구조도 피한다.

익명 uid는 한 계정을 구분하지만 실제 직원 한 명을 증명하지는 않는다. 가벼운 친목용 파일럿은 그 한계를 명시해 운영할 수 있다. 결과 신뢰가 중요한 투표·경품으로 확대할 때에는 주최자 승인 명단이나 일회성 참가 자격 등으로 1인 다중 계정 문제를 다뤄야 한다. 또한 현재 `completed`는 클라이언트가 보내는 값이므로 완료 보고 자체를 엄격한 청취 증명으로 간주하지 않는다.

## 6. 그룹 중심과 개인 중심의 비교

아래는 현재 코드와 사용 목적에 기반한 전략 판단이며, 시장 조사로 입증된 경쟁 우위나 예상 매출이 아니다.

| 판단 축 | 회사 안의 소규모 그룹 | 개인 창작·감상 |
| --- | --- | --- |
| 첫 사용 이유 | 주최자가 정한 행사와 동료의 참여 | 창작 욕구, 소리 놀이, 링크 구경 등 동기가 다양함 |
| 초기 관객 | 초대한 사람들로 시작 가능 | 알려지지 않은 창작자의 첫 관객 확보가 과제 |
| 자연스러운 재방문 | 다음 회차·투표 마감·결과 발표 | 다시 만들 소재, 이어 만들기, 반응·취향의 축적 |
| 주요 이탈 위험 | 행사 한 번으로 끝남, 주최자 노동, 의무 참여 | 첫 재미 이후 소재 부족, 제작 부담, 반응 부족 |
| 우선 만들 것 | 회차 운영, 목적이 유지되는 제출, 결과, 다음 회차 | 빠른 첫 완성, 자기 작품 변형, 취향에 맞는 반복 과제 |
| 성공을 보는 단위 | 주최자·그룹의 재개최 + 참가자의 다음 회차 재참여 | 창작자의 다른 날 재창작 + 감상자의 의미 있는 재방문 |
| 비용이 커지는 방향 | 기업 권한 관리·명단·신뢰 가능한 투표 | 공개 콘텐츠 공급·발견·운영·지속적인 소재 제공 |

**그룹 우선의 근거:** 지금은 누구에게 보여줄지, 왜 같이 참여할지까지 정의할 수 있는 쪽이 더 빠른 학습 경로다. 창작 엔진을 유지하면서 초대와 반복 활동을 묶을 수 있다.

**그룹 우선에 대한 반론:** 회사 놀이가 본질적으로 일회성일 수 있다. 주최자가 요청해서 참여하는 사용자를 자발적 팬으로 오해하기 쉽다. 창작 단계 없이 이름만 넣는 추첨 도구를 더 원한다면, 키크의 창작 경험과 고객의 요구가 맞지 않을 수도 있다.

**개인 중심으로 바꿀 근거:** 초대 없이 반복해서 만드는 개인이 실제로 있고, 예시 변형·자기 작품 복제만으로 재창작이 늘어나며, 그룹은 다음 회차 수요가 약한 경우다. 이때 개인용 범용 SNS를 만드는 대신 관찰된 반복 사용 장면 하나에 집중한다.

두 방향을 같은 비중으로 크게 개발하지 않는다. 초반에는 공통 첫 완성 개선과 작은 그룹 반복 실험을 실행하고, 개인용은 자기 작품 변형 정도로 범위를 제한한다.

## 7. 권장하는 그룹 경험

### 사용자가 보는 흐름

**이번 회차 주제 확인 → 예시에서 내 작품 만들기 → 이 회차에 제출 → 동료 작품 감상 → 선택 또는 추첨 결과 확인 → 다음 회차 참여.**

예를 들어 ‘이번 주 우리 팀을 소리 네 개로 표현하기’를 열고, 제출 다음 날 짧게 감상하고, 금요일 모임에서 결과를 본다. 주최자는 결과 화면에서 다음 주 주제를 골라 같은 멤버로 새 회차를 연다. 이 일정은 검증용 예시이며 모든 조직에 매일 창작을 요구하지 않는다.

### 첫 제품 실험에 넣을 범위

1. **그룹·회차 문맥 유지:** `groupId`와 `roundId`를 작성 흐름에 보존한다. 공유 설정을 처음 열었을 때 해당 회차를 보여주고 기본 대상을 유지한다. 제출 후 그 회차로 돌아온다.
2. **가벼운 참여:** 회사 주제에 맞는 예시 몇 개와 한 부분만 바꾸는 경로를 제공한다. 원하면 상세 편집으로 확장한다.
3. **주최자 운영:** 모집·제출·감상/선택·결과 상태를 보여준다. 최초 검증에서는 복잡한 예약 자동화보다 주최자의 명시적 상태 전환을 먼저 구현할 수 있다.
4. **결과와 다음 회차:** 결과를 고정해서 보관하고, 동일 그룹의 다음 회차를 복제한다. 지난 회차의 표·청취 기록은 새 회차와 분리한다.
5. **재방문 진입점:** 홈에서 진행 중인 회차나 새 결과로 바로 들어간다. 초대는 수동 코드 외에도 코드가 채워지는 링크·QR로 연결한다. 자동 가입 대신 대상 확인 후 입장한다.

첫 파일럿은 ‘함께 감상하기 + 참가자 추첨’과 ‘선호 투표’ 중 주최자가 실제로 필요한 **한 모드**를 고른다. 두 모드의 점수를 혼합하지 않고, 확인되지 않은 관리 기능까지 한 번에 구현하지 않는다.

알림은 받을 가치가 있는 사건이 생긴 다음 붙인다. 초반에는 주최자가 공유할 다음 회차 안내·결과 안내 문구와 링크를 제공해 기존 팀 채널에서 전달하게 할 수 있다. 이것은 제품 제안이며, 이번 분석 과정에서 누구에게도 메시지를 보내지 않았다.

### 100명 한도와 실제 참여 부담은 다르다

100명이 작품을 하나씩 내고 본인 작품을 제외한 99개를 각각 15초씩 듣는다면, 순수 재생 시간만 1인당 24분 45초다. 화면 이동과 작품 만들기는 포함하지 않은 계산이다. 정원이 100명이라는 사실이 전수 감상도 가볍다는 뜻은 아니다.

파일럿은 작은 팀으로 시작하고 전체 청취를 의무로 만들지 않는다. 작품이 많아지면 감상 큐와 균등한 노출을 검토하되, 서로 다른 일부 작품만 본 사람들의 원시 득표수를 곧바로 공정한 전체 순위로 해석하지 않는다. 큰 그룹의 선호 투표에는 후보 축소·결선 또는 별도의 평가 설계가 필요하다. 참가자 추첨은 이 문제를 피해 갈 수 있지만, 작품 선호 투표를 대체했다고 설명해서는 안 된다.

## 8. 개인 사용자에게 공통으로 개선할 것

### 첫 경험을 설명보다 체험에 가깝게 만든다

현재의 기본 키캡을 살리되, 첫 화면에서 짧은 완성 예시를 직접 눌러 보고 한 부분을 바꾸도록 한다. 안내를 보았는지보다 첫 소리를 내고, 수정하고, 완성했는지를 본다. 긴 안내가 실제 이탈 원인인지는 전환 지표로 검증한다.

### 로컬 완성과 온라인 공유를 구분한다

홈은 공유 상태를 기준으로 공유되지 않은 작품을 초안처럼 다룬다. 그러나 개인 사용자는 공유하지 않고도 만족스러운 작품을 완성할 수 있다. ‘완성’과 ‘게시됨’을 별도 상태로 표현하고, 완성작 재생·복제·편집을 선택하게 한다. 공개 공유를 재방문의 필수 조건으로 만들지 않는다.

### 재창작 비용을 낮춘다

우선 자기 작품의 ‘다른 버전 만들기’, 최근 사용한 설정, 운영자 예시에서 시작하기를 제공한다. 공개 리믹스는 원본 자산의 재사용 범위와 출처 표시를 정한 뒤 확장한다. JSON 복제만으로 끝나지 않으며, 새 작품 ID·자산 소유권·원작 공유 중단 시 동작까지 설계해야 한다.

### 미션에 참여와 결과를 붙인다

현재 날짜별 문구를 ‘이번 주 주제 → 내 작품 연결 → 지난 참여 보기’로 발전시킬 수 있다. 매일 만들어야 하는 부담보다 실제 창작 주기에 맞는 빈도를 먼저 확인한다. 연속 방문 배지나 포인트만으로 소재 부족을 해결하려고 하지 않는다.

### 저장을 믿을 수 있게 한다

`state.tsx`는 저장 실패를 콘솔 경고로 남기고 진행을 허용한다. 첫 경험을 계속할 수 있다는 이점은 있지만, 사용자가 저장됐다고 생각한 작품이 다음에 없으면 재방문 가치가 무너진다. 저장 실패 상태·재시도·백업 여부를 사용자에게 구별해 보여주고 복구 코드는 이미 만든 것이 생긴 시점에 안내한다.

## 9. 측정 설계

### 전체 재방문율 하나로 판단하지 않는다

| 구분 | 시작 사건 | 재방문으로 인정할 핵심 행동 | 우선 볼 기간 |
| --- | --- | --- | --- |
| 개인 창작자 | 첫 작품 완성 | 다른 날짜에 두 번째 작품 완성 | 7일 이내·28일 이내 누적 재창작 |
| 링크 감상자 | 첫 리플레이 완료 | 다른 날짜의 감상·직접 체험, 또는 첫 창작 | 7일·28일, 감상과 창작 전환 분리 |
| 그룹 참가자 | 첫 회차의 제출 또는 유효 참여 | 동일 그룹의 다음 회차에서 다시 유효 참여 | 다음 개최 시점 기준 |
| 그룹 주최자 | 첫 실제 회차 개최 | 참가자가 실제 활동한 두 번째 회차 개최 | 28일 이내, 필요하면 조직 주기에 맞춰 확대 |

‘D7 당일 복귀’와 ‘7일 안에 한 번이라도 복귀’는 다른 지표다. 우선 다른 날짜의 두 번째 가치 행동을 누적으로 보고, 필요하면 D1·D7 당일 지표를 보조로 둔다. 시작·복귀 사건을 명시해야 한다는 원칙은 [Amplitude의 리텐션 정의](https://www.amplitude.com/docs/analytics/charts/retention-analysis/retention-analysis-build)를 참고했다. 회사 행사를 일간 지표 하나로 판단하지 않는 이유는 [실제 사용 주기에 맞춘 분석](https://www.amplitude.com/docs/analytics/charts/retention-analysis/retention-analysis-interpret-usage)에 있다. 이 문서들은 측정 개념의 근거이며 특정 분석 서비스 도입 권고는 아니다.

### 퍼널과 결과를 함께 본다

- 개인: 진입 → 예시 체험/새 작품 시작 → 첫 수정 → 공연 완료 → 로컬 완성 → 선택적 공유 → 다른 날 재창작.
- 그룹: 초대 확인 → 입장 → 회차 확인 → 제출 또는 감상/선택 → 결과 확인 → 다음 회차 참여.
- 주최자: 회차 열기 → 실제 참가자 활동 → 결과 확정 → 다음 회차 생성 → 다음 회차 실제 활동.

현재 `workStats`와 그룹 `listens`에는 재생·청취 집계가 있지만, 이것만으로 위 퍼널과 개인 재창작 코호트를 복원하기는 어렵다. `src`, `functions/index.js`, `package.json`, `index.html` 검색에서 일반적인 분석 이벤트 계측은 확인하지 못했다. 운영 환경에 별도로 존재하는 통계까지 없다고 단정하지는 않는다.

추가할 이벤트 후보는 `creation_started`, `first_edit`, `performance_completed`, `work_completed`, `publish_succeeded/failed`, `group_joined`, `round_opened`, `entry_submitted/failed`, `replay_completed`, `vote_cast`, `result_viewed`다. 뒤의 회차·투표 이벤트는 신규 기능과 함께 정의한다. 서버에서 확정되는 제출·투표·결과 사건은 클라이언트 클릭과 구분해 집계한다.

### 해석 오류를 막는 규칙

1. 웹·토스, 직접 진입·공유 링크·그룹 초대, 개인·그룹 역할을 구분한다. URL 전체나 초대 코드 대신 제한된 출처 분류만 저장한다.
2. 그룹 주최자 재개최율의 분모는 관찰 기간이 끝난 첫 개최 그룹으로 한다. 두 번째 행사 의향만 말한 그룹, 빈 회차를 만든 그룹은 성공으로 세지 않는다.
3. 참가자 재참여는 첫 회차 참가자 전체 기준과 다음 회차 참여 기회가 있었던 사람 기준을 함께 본다. 두 번째 회차가 열린 그룹만 보면 주최자 이탈을 숨길 수 있다.
4. 회차별 행동은 같은 세션에 여러 번 들어온 것과 구분한다. 페이지 새로고침을 재방문으로 세지 않는다.
5. 익명 계정·브라우저 저장소 초기화·기기 변경으로 사람이 나뉠 수 있음을 기록한다. 확인 가능한 계정 연결만 사용하고 기기 지문으로 억지로 합치지 않는다.
6. 평균만 제시하지 말고 표본 수, 완료 비율, 첫 완성 시간의 중앙값과 느린 구간을 함께 본다. 각 회사가 하나의 실험 단위이므로 회사 안의 참가자 수를 독립 표본처럼 부풀리지 않는다.

### 기존 데이터 수집 약속을 지킨다

README에는 행태정보 수집을 넣지 않는다는 원칙이 있다. 위 이벤트 목록은 도입된 기능이 아니라 **측정 요구사항 초안**이다. 이 약속을 바꾸지 않고 일반 사용자에게 분석 SDK부터 붙이는 것은 권하지 않는다.

첫 파일럿에서는 참여자가 이해한 범위의 성인 팀 테스트, 주최자의 회차 운영 기록, 기존 서버의 서비스 운영 집계를 우선 사용한다. 사용자 단위 장기 코호트가 필요하다면 수집 목적·항목·보관 기간·선택권을 먼저 정하고 제품 안내와 맞춘다. 녹음·그림·작품 제목·회사 이름·복구 코드·초대 코드 원문은 분석 페이로드에 넣지 않는다. 집계만으로 알 수 없는 것은 별도 인터뷰로 보완하고 추정치를 실제 리텐션 수치처럼 제시하지 않는다.

## 10. 4~6주 검증 계획과 집중 방향 결정

아래 기간과 기준은 작업을 작게 제한하기 위한 제안이다. 업계 평균이나 이미 달성한 수치가 아니다. 비공개 자산 경로를 바꾸는 범위가 커지면 일정은 별도 산정한다. 그 전에는 민감한 회사 콘텐츠를 쓰는 테스트를 확대하지 않는다.

### 1주차: 누구에게 무엇이 실패하는지 확인

- 확보 가능한 운영 데이터로 유입·역할·활성화 여부를 분리한다. 실제 코호트 데이터가 없으면 그 한계를 기준선에 표시한다.
- 주최자 3~5명과 개인 사용자 5명 안팎에게 첫 사용 관찰과 후속 인터뷰를 진행한다. 인원은 탐색용이며 통계적 대표성을 주장하지 않는다.
- ‘다시 쓰시겠어요?’보다 마지막으로 사용한 상황, 다시 쓰려고 했다가 그만둔 단계, 다음에 실제로 필요한 날짜를 묻는다.
- 그룹 참가자가 창작을 즐겼는지, 행사·경품 때문에 했는지, 주최자가 어떤 준비를 대신 해줬는지를 구분한다.

### 2~3주차: 반복에 필요한 최소 연결 구현

- 그룹·회차 문맥을 보존한 만들기/제출, 첫 예시 변형, 제출 성공·실패 피드백을 우선 연결한다.
- 선택한 한 행사 모드의 마감·결과 확정·다음 회차 복제를 구현한다. 초기 마감은 주최자 수동 전환이어도 서버가 상태를 검사해야 한다.
- 개인에게도 도움이 되는 자기 작품 복제와 로컬 완성 표시를 작은 범위로 검증한다.
- 필요한 비공개 범위, 투표·추첨 자격을 정하고 아래의 서버 검증을 갖춘다.

### 4~6주차: 실제 두 번째 사용 관찰

- 작은 팀 3~5곳에서 두 번의 사용 기회를 관찰한다. 첫 회차 진행 지원과 두 번째 회차의 지원 수준을 기록한다.
- 가능한 경우 두 번째 회차는 개발자의 개별 독촉 없이 주최자가 준비하게 한다. 제품이 제공한 안내와 사람이 대신 수행한 일을 구분한다.
- 같은 기간 개인 경로에서는 예시 변형·자기 작품 복제 이용자의 다른 날 재창작을 본다. 유입과 사용자 특성이 다른 그룹·개인의 원시 재방문율만 직접 비교하지 않는다.

### 투자 판단의 구체적인 기준

예를 들어 유효한 파일럿 그룹 5곳을 확보했다면, 다음 규칙을 실험 전에 고정한다.

| 관찰 결과 | 다음 판단 |
| --- | --- |
| 5곳 중 3곳 이상이 관찰 기간 안에 두 번째 실제 회차를 열고, 반복 그룹의 참가자 재참여율 중앙값이 40% 이상이며 주최자 부담이 줄어듦 | 그룹 중심 투자를 한 단계 확대 |
| 두 번째 개최가 0~1곳이고, 주된 이유가 ‘행사가 다시 필요하지 않음’ | 그룹을 상시 재방문 성장축으로 보는 가설을 낮춤 |
| 주최자는 반복하려 하지만 제작·제출·감상 단계에서 막힘 | 고객 방향을 바로 바꾸기보다 해당 퍼널을 한 번 더 개선 |
| 주최자는 이름만 넣는 추첨을 원하고 창작을 반복해서 생략함 | 별도 추첨 도구로 전환할지의 사업 판단이 필요하며, 키크 그룹의 성공으로 해석하지 않음 |
| 초대 없이 다시 만드는 개인이 관찰되고, 좁은 개인 실험에서 재창작이 반복됨 | 그 개인 사용 장면에 집중하는 후속 실험으로 이동 |
| 중간 결과이거나 관찰 기간·표본이 부족함 | 성공을 선언하지 말고 기간 또는 팀 수를 제한적으로 추가 |

40%는 통계적 유의성이나 시장 적합성의 기준이 아니라 사전에 정하는 파일럿 의사결정선이다. 재참여의 유효 행동은 행사 모드에 따라 제출·감상·선택 중 무엇인지 미리 정한다. 결과 페이지 열람만으로 창작 재참여를 주장하지 않는다.

그룹 방향에서 초기 핵심 지표는 **기간 내 두 번째 실제 회차를 개최한 그룹 수와 비율**이다. 참가자 재참여, 첫 완성 시간, 주최자 준비 시간, 지원 요청을 함께 봐서 ‘사람을 모았지만 쓰기 힘든 제품’인지 구분한다. 개인 중심으로 전환하면 핵심 지표는 **첫 완성자 중 다른 날 다시 완성한 창작자 비율**로 둔다.

### 2026-09-17 구현 상태

- **P0 접근 정합성: 구현·로컬 검증 완료.** 그룹 전용 작품은 `visibility: group`과 `groupWorks/` 비공개 경로를 쓰며, 작품·자산·썸네일 모두 callable에서 현재 멤버십을 확인한다. 공개 링크 작품의 기존 동작은 유지한다.
- **P0 측정: 정의 완료, 수집은 보류.** 이 문서의 분모·기간·가치 행동을 기준선으로 삼는다. 아직 별도 분석 저장소나 이벤트 파이프라인을 추가하지 않았으므로, 파일럿 시작 전에 개인정보 범위와 보존 기간을 확정해야 한다.
- **P1 그룹 진입/제출과 회차: 구현·로컬 검증 완료.** 그룹에서 시작하면 `g` 컨텍스트가 만들기→무대→공연→카드→공유까지 유지되고, 그룹 전용 제출은 공개 링크를 만들지 않는다. 운영자는 회차를 마감해 순위 스냅샷을 남기고 다음 회차를 열 수 있다. 마감 뒤 재생은 결과 집계를 바꾸지 않는다.
- **P1 첫 완성·저장 실패 UX: 구현·로컬 검증 완료.** 첫 `새로 만들기`는 긴 안내 화면을 거치지 않고 바로 연주 가능한 기본 키캡으로 시작한다. 자동 저장은 계속 비차단으로 동작하지만, 실패 시 제작·무대·공연·카드 화면에 재시도 버튼을 표시한다. 목적별 예시, 실제 소요 시간 측정, 정식 투표/추첨 규칙은 다음 작업이다.

P0/P1은 심각도와 의존성을 표시한다. 모든 항목을 먼저 완성해야 사용자 관찰을 시작할 수 있다는 의미는 아니다. 민감하지 않은 예시와 명확한 안내로 첫 경험 관찰은 병행할 수 있다.

### 코드에서 확인한 추가 개선 후보

- **그룹 일부 제출 실패가 성공으로 보일 수 있음:** `publishWork`는 `submitted.length === 0`일 때만 의미 있는 `skipped`를 `groupError`로 올린다. 일부 그룹은 성공하고 다른 그룹은 가득 찬 경우 등은 그룹별 결과가 충분히 전달되지 않는다. 선택한 대상별 성공·실패·재시도 상태를 반환하고 보여주는 것이 맞다.
- **공유 대상과 확인 문구의 연동이 불완전함:** `ShareGate`는 확인 체크를 `hasGroups` 변경에만 초기화한다. 그룹이 선택된 채 공개 스테이지를 추가해도 체크 상태와 그룹용 확인 문구가 유지될 수 있다. 최종 공개 대상 전체를 기준으로 확인 내용과 상태를 결정해야 한다.
- **느린 목록 요청 중 필터 변경 경합 가능성:** `GroupStageScreen.load`는 요청 중이면 새 호출을 반환하며, 그 뒤에야 `requestId`를 증가시킨다. 이전 요청이 진행 중일 때 정렬·검색이 바뀌면 새 요청은 빠지고 이전 응답이 반영될 수 있다. 정적 코드에서 도출한 재현 후보이며 실제 기기 재현은 하지 않았다. 조건 변경 시 세대를 먼저 무효화하고 새 요청을 보장하는 방식으로 정리한다.
- **공식 투표 운영에 필요한 서버 제약 부족:** 제출 한도 확인과 batch 쓰기가 분리돼 있어 동시 제출 시 한도·카운트 일관성을 별도로 검증해야 한다. 완료 보고도 클라이언트 값이다. 현재의 가벼운 감상 집계를 금전적 이해가 걸린 투표·추첨의 신뢰 기반으로 그대로 확대하지 않는다.

이 항목들은 재방문 하락의 확인된 원인이 아니라, 반복 행사에 투자할 때 신뢰와 실패 복구를 해칠 수 있는 코드상의 문제다.

### 회차 모델의 최소 방향

그룹은 멤버십을 유지하고, 회차 아래에 제출·청취·선택·결과를 둔다. 예시 구조는 `groups/{groupId}/rounds/{roundId}`와 그 하위의 `entries`, `listens`, `ballots`, `result`다. 실제 스키마는 첫 행사 모드를 고른 뒤 확정한다.

서버는 phase와 마감, 제출 자격, 투표 수 제한, 자기 투표 정책을 검사한다. 결과 확정·추첨은 트랜잭션과 멱등 키로 재시도해도 바뀌지 않게 한다. 회차에 제출한 작품은 버전 또는 스냅샷을 고정해 투표 도중 편집으로 내용이 달라지지 않게 한다. 기존 그룹의 제출·청취 기록을 새 회차의 표로 자동 재사용하지 않는다.

대규모 재작성보다 `functions/index.js`의 그룹·청취·회차 처리를 경계별로 나누고, 화면에서는 목록 조회와 주최자 제어를 분리하는 정도부터 진행한다. 오디오 엔진 전체 재설계는 이번 재방문 과제의 우선순위가 아니다.

추가 검증은 실제 위험에 맞춘다: 비멤버·탈퇴 후 자산 접근, 동시 제출과 중복 투표, 마감 직전 요청, 결과 확정 재시도, 그룹 일부 제출 실패, 저장 실패, 느린 목록 응답 중 필터 변경, 모바일 녹음 거부와 재생 복구. 기존 단위 테스트가 통과했다는 이유로 이 경로가 검증됐다고 보지 않는다.

## 12. 지금 뒤로 미룰 것

- 새 재질·LED·흔적 프리셋의 대량 확장: 이미 표현 도구가 다양하며 반복 목적을 만드는 문제와 거리가 있다.

- 접속 보상·연속 방문 강제: 조직 행사와 개인 창작의 실제 주기를 먼저 확인한다.
- SSO·조직도·정교한 관리자 콘솔: 작은 팀의 재개최가 확인되기 전에는 구현 범위를 제한한다.
- 영상 내보내기·광범위한 리믹스 계보: 첫 완성과 두 번째 창작에서 필요한지 증거를 모은 뒤 투자한다.
